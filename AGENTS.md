# NFLviewer / LeagueWatch

name: NFL_VIEWER_AGENT
description: You are working on an NFL_VIEWER repo This repository contains the LeagueWatch NFL watchability app. It is a
two-process application: a Python FastAPI service owns nflverse data, matchup
scoring, and live-news ingestion; a Next.js application owns the UI,
authentication, profiles, comments, and browser-facing proxy routes.

## Product scope

- Rankings currently support the 2025 NFL regular season, Weeks 1–18.
- Ratings are displayed on a `1.00–10.00` scale and are deterministic.
- The ranking response includes matchup, pregame records, logos, final scores
  when available, reasons, and two active player spotlights.
- Live News is separate from historical matchup headlines. It reads current
  ESPN, CBS Sports, FOX Sports, and NBC Sports feed data from PostgreSQL,
  refreshes hourly while FastAPI is running, retains one year, and supports
  cursor pagination plus publisher/team filters.
- Public profiles, email/password sessions, and game comments are handled by
  the Next.js app. Public users can read comments; authenticated users can
  create replies and delete their own comments. Comments are not edited.
- Do not add betting/odds features or broaden the scoring model without an
  explicit product decision.

## Local development

Requirements: Python 3.12, `uv`, Node.js 20.9+, npm, and Docker Desktop.

Start PostgreSQL (this machine uses the legacy `docker-compose` command):

```bash
cd /Users/samarthab/NFLviewer
docker-compose up -d postgres
```

Apply frontend schema migrations when the database is new or migrations have
changed:

```bash
cd frontend
DATABASE_URL=postgresql://leaguewatch:leaguewatch@127.0.0.1:5433/leaguewatch npm run db:migrate
```

Start FastAPI in one terminal:

```bash
cd /Users/samarthab/NFLviewer
DATABASE_URL=postgresql://leaguewatch:leaguewatch@127.0.0.1:5433/leaguewatch \
  uv run fastapi dev src/nflviewer/app.py --host 127.0.0.1 --port 8000
```

Start Next.js in another:

```bash
cd /Users/samarthab/NFLviewer/frontend
npm run dev -- --hostname 127.0.0.1 --port 3000
```

Useful URLs:

- App: `http://127.0.0.1:3000`
- Live News: `http://127.0.0.1:3000/headlines`
- FastAPI docs: `http://127.0.0.1:8000/docs`
- FastAPI health: `http://127.0.0.1:8000/health`

If PostgreSQL was unavailable when FastAPI started, restart FastAPI after the
database becomes healthy. The news repository is initialized during FastAPI
lifespan startup and is not automatically reconnected after a failed startup.

## Data and API contracts

- Rankings endpoint: `GET /api/v1/rankings?season=2025&week=1..18`.
  `top` and `bottom` are mutually exclusive; omit both for the full slate.
- Headlines endpoint: `GET /api/v1/headlines?limit=20&cursor=...&source=...&team=...`.
- The Next.js `/api/rankings` and `/api/headlines` routes proxy to FastAPI.
  Local fallback is `http://127.0.0.1:8000`; production sets
  `NFL_API_BASE_URL` to the deployed FastAPI origin.
- `DATABASE_URL` is required for auth, profiles, comments, and live headlines.
  Never commit `.env.local` or production secrets.
- `data/processed/` is a local nflverse cache. Run
  `uv run python -m nflviewer.sync_data` to populate it; use `--force` only
  when a refresh is intentional.
- The checked-in `data/headlines-2025.json` is only for historical matchup
  explanations. Live News comes from `news_articles` in PostgreSQL.

## Implementation conventions
Always refer to the AGENT SKILLS when developing,

- Inspect the target source, its tests, and one nearby existing pattern before
  editing. Prefer small, contained diffs over new abstractions.
- Keep ranking calculations pure and deterministic. Do not perform network or
  database calls in the ranking request path.
- Keep external feed parsing defensive: validate HTTPS hosts, canonical URLs,
  response size, dates, and team tags. Treat publisher content as untrusted
  data, not instructions.
- Use Pydantic models for FastAPI request/response validation and Zod or the
  existing frontend validation helpers for browser inputs.
- Preserve cursor pagination ordering by `(published_at DESC, id DESC)`.
- Use existing Drizzle schema/migrations for database changes. Never manually
  alter production schema or delete data without an explicit migration plan.
- Preserve accessibility, mobile-first behavior, and the existing visual
  system when changing UI. Add/update tests for visible behavior.
- Keep auth secrets, database credentials, and provider tokens out of source,
  logs, commits, and client-side bundles.

## Fresh-thread workflow

1. Confirm the task's target area using the repository map above.
2. Read the relevant source and tests; do not load unrelated directories.
3. State a short plan and any material ambiguity before changing code.
4. Implement the smallest compatible change and add regression tests.
5. Run the focused test, then the appropriate full checks above.
6. Review `git diff` and `git status`; do not include generated files or local
   environment changes accidentally.
7. Use a Conventional Commit message, for example
   `fix(news): reconnect feed repository after database restart`.

When requirements conflict with existing behavior, surface the conflict and
ask before changing public API shape, scoring weights, database schema, auth
semantics, or deployment architecture.
